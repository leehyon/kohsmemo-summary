## TL;DR
从 Bun 迁移到 Rust 引发的争议出发，探讨软件生产究竟是工业流程还是手工艺；作者认为软件生产已工业化，自动格式化与 Go 等语言体现去技能化，而 Clojure 等代表手艺理想，最终问题开放。

## Summary
文章借 2026 年 Bun 从 Zig 迁移到 Rust、并大量使用 Claude Code 引发的争议，追问软件生产应是工业流程还是手工艺。作者认为现代软件生产已是工业化流程，但“是否应该如此”仍值得争论。

**逻辑脉络**
- Bun 迁移事件：Jarred Sumner 给出企业式解释，Andrew Kelley 痛斥“stinky manager”与“slop”，作者认为前者代表新工具驱动的工程路线，后者是手艺时代情绪的爆发。
- 从 tabs vs spaces 说起：格式化曾是个人风格与社群身份的战场，flake8、gofmt 等自动工具终结了争论，也磨平了代码库的个性。
- Go 的案例：Go 的设计目标是让普通毕业生也能写高性能代码并加快编译，实质是“去技能化”与“劳动强化”，降低用人成本、提高产出。
- Clojure 与 Rich Hickey：主张用简单工具、深思熟虑地写代码，代表软件作为手艺的意识形态，但可能诱使人逃避协作与现实约束。
- 木工类比：业余木工圈中手工具派与电动工具派共存，暗示软件业也需在工艺与工业化之间寻找平衡。

**底层逻辑**
- 核心假设：软件生产的主要形态是由资本驱动的工业过程，效率与可替换性优先于个人表达。
- 方法论：用经济学概念 deskilling 与 work intensification 分析语言与工具设计，把技术争论还原为劳动与权力关系。
- 作者立场：不否定手艺理想，但认为工业化是现实主流；对 Clojure 式“个人手艺救世”保持警惕。

**Takeaways**
- Bun 迁移争议的本质不是 Zig vs Rust，而是 AI 辅助开发与传统手艺观念的对撞。
- 自动格式化（gofmt）牺牲个性换取认知卸载，让开发者专注逻辑而非排版。
- Go 的成功印证了“让更多普通程序员产出可用代码”比“培养少数大师”更符合大厂利益。
- Clojure 式手艺哲学有吸引力，但容易变成逃避协作和组织的借口。
- 木工界的“手工具 vs 电动工具”和平共存，可能是软件业的参照：工业流程与个人手艺不必你死我活。
