# 用 LLM 管理安全开发规范

## TL;DR
本文介绍基于 llm-wiki 理念，利用 LLM 构建三层知识系统。通过将分散文档“编译”结构化，解决检索维护难题。该方案降低了维护成本，提升了问答精准度，实现了知识库的可持续发展。

## Summary
核心主题：基于 Karpathy 的 llm-wiki 理念，利用 LLM 构建三层架构的知识管理系统，解决安全开发规范文档分散、检索困难及维护成本高的问题。

关键信息：

*   **背景与理念**
    *   **痛点**：安全规范文档格式不一、散落在各处（Word、Notion 等），新人入职学习成本高，故障复盘经验难以复用。
    *   **核心思路**：引入 Wiki 中间层作为“编译器”，将混乱的 Raw 层文档编译为结构化的 Wiki 层，再输出为人类可读的 Output 层文档。实现了从“存与找”到“编译与查询”的转变。

*   **实施步骤**
    1.  **生成操作手册 (CLAUDE.md)**：基于 Karpathy 的 Gist 生成，定义三层架构、Wiki 页面规范（frontmatter、交叉引用规则）、摄入工作流及 Lint 检查机制。
    2.  **收集原始素材**：将 PDF、Word、Markdown 等格式的安全规范文档、故障复盘报告统一放入 Raw 目录，保持原貌不做格式清洗。
    3.  **生成 Wiki 层**：使用 LLM 读取原始素材并生成结构化 Wiki 页面，经过 5-6 轮人工交互迭代，完善交叉引用、补充缺失的概念页面并理清逻辑关系。
    4.  **生成最终文档**：基于 Wiki 层生成面向开发者的最终规范文档，包含“为什么”的解释及关联的真实故障案例链接。

*   **实际效果**
    *   **阅读体验**：支持 Obsidian 阅读，规范条目直接链接到相关故障案例（如 SQL 注入规范链接具体漏洞事故），不仅知其然，亦知其所以然。
    *   **LLM 问答**：基于结构化 Wiki 层查询，回答精准度大幅提升，能结合概念页面与事故案例给出具体建议。
    *   **持续更新**：仅需将新素材放入 Raw 目录并提示 LLM，即可自动更新 Wiki 层与最终文档，维护成本显著降低。

*   **问题与解决方案**
    *   **Wiki 质量不稳定**：细化 CLAUDE.md 规范，强制要求 Summary 行、Tags 标记及特定页面结构（如事故案例必须包含攻击向量、修复方案等）。
    *   **交叉引用断裂**：强化双向链接规则（A 引用 B 则 B 必须引用 A），并引入定期 Lint 检查以修复断链与孤儿页面。
    *   **非结构化素材效率低**：对截图、聊天记录等低质量素材进行手动预处理，转为结构化 Markdown 后再输入。

逻辑脉络：

文章首先指出传统文档管理在安全规范维护上的痛点，进而引入 llm-wiki 的“编译”理念作为突破口。随后详细阐述了从定义 CLAUDE.md 规范、收集多格式原始素材、到通过多轮迭代生成结构化 Wiki 层，最终输出人类可读规范文档的具体实施过程。接着展示了该方案在提升阅读体验、精准问答及降低维护成本方面的实际效果，并针对实施中遇到的质量、引用及非结构化数据处理问题提供了具体解决方案。最后总结指出，该方法本质上是将“文档管理”转化为“知识工程”，利用 LLM 承担维护工作，实现了知识库的可持续发展。
