# Beyond SOLID: Embracing CUPID for Modern Software
- URL: https://dzone.com/articles/beyond-solid-embracing-cupid-for-modern-software
- Added: 2026-05-26 10:00:45
- Tags: #design #engineering

## TL;DR
文章提出用 CUPID 属性替代 SOLID 原则，以适应现代开发。CUPID 强调组合性、可预测性等行为表现，旨在提升开发者体验与代码可维护性，构建更易理解的软件系统。

## Summary
核心主题：文章提出用 CUPID 属性替代传统的 SOLID 原则，以适应现代软件开发环境，强调代码的可维护性、开发者体验与业务对齐。

逻辑脉络：
1.  **背景演变**：SOLID 原则虽是 OOP 的黄金标准，但在微服务、Serverless 和动态语言普及的当下，过度遵守会导致过度设计和认知负荷过重。
2.  **概念引入**：CUPID 由 Dan North 提出，它不是强制执行的规则，而是代码应具备的“属性”，关注系统的行为表现而非仅仅是构建结构。
3.  **详细阐述**：文章逐一拆解 CUPID 的五大核心属性，并对比 SOLID 阐述其在现代开发中的优势。
4.  **实践与展望**：提供基于 CUPID 的代码审查清单，探讨 AI 在实现 CUPID 属性中的辅助作用与局限性，总结其对构建高质量软件的意义。

关键信息：

1.  **Composable (组合性)**
    *   **定义**：将小型、独立的片段组合成大型系统的能力，组件间粘合层薄，互不干预内部。
    *   **实践**：摒弃紧耦合的对象调用，采用“Data-In, Data-Out”的函数式转换，使测试变得简单（无需复杂 Mock），逻辑易于链式调用。

2.  **Unix-inspired (Unix 哲学启发)**
    *   **定义**：遵循“做一件事并做好”的原则，模块应像管道一样协作。
    *   **实践**：避免“上帝对象”或“管理器”类；使用标准数据结构（如 JSON、Lists）作为接口，而非深层的自定义对象。

3.  **Predictable (可预测性)**
    *   **定义**：代码行为必须完全符合预期，无副作用或隐藏状态。
    *   **实践**：具备可观察性（错误信息明确）、确定性（相同输入必有相同输出）、无隐式副作用（如 `get_user_balance` 不应刷新 Token），遵循“最小惊讶”原则。

4.  **Idiomatic (符合语言习惯)**
    *   **定义**：代码应顺应特定编程语言的惯用写法，而非生搬硬套其他语言的范式。
    *   **实践**：例如在 Python 中应使用列表推导式而非 Java 风格的循环处理，以减少阅读摩擦，提升代码的本地化程度。

5.  **Domain-driven (领域驱动)**
    *   **定义**：代码应反映解决的真实世界问题，而非技术栈细节。
    *   **实践**：使用业务领域的通用语言命名变量和函数（如 `submit_insurance_claim`），消除技术与业务团队的“翻译税”。

6.  **SOLID 与 CUPID 的对比**
    *   **SOLID**：关注微观的类与接口结构，旨在通过原则规则最小化技术债务。
    *   **CUPID**：关注宏观的系统行为与开发者体验，旨在通过属性最大化开发的愉悦感与系统的适应性。

7.  **实施建议与 AI 角色**
    *   **应用**：在 Code Review 中询问代码是否具备组合性、单一职责、可预测性、语言习惯及业务领域相关性。
    *   **AI 辅助**：AI 擅长提升代码的“符合语言习惯”和“可预测性”（如重构、生成测试），但难以理解特定业务上下文，因此“领域驱动”设计仍需人工架构师把控。

8.  **总结**
    *   CUPID 并非否定 SOLID，而是适应高速度开发和 AI 辅助时代的演进，优先考虑清晰度与简洁性，构建富有生命力且易于维护的软件系统。
