# The 20 Software Engineering Laws

## TL;DR
软件开发是人、时间与系统的博弈。本文总结了系统设计、组织架构、时间估算及团队管理的核心定律，揭示了协作与项目本质，帮助工程师预判问题并理解现状。

## Summary
核心主题：软件开发不仅是代码编写，更是人、时间与系统的博弈。这些定律揭示了团队协作、系统设计及项目管理的本质规律，虽非指导规则，却能帮助工程师预判问题、理解现状。

逻辑脉络与关键信息：

1. 系统设计与复杂性
   - Gall’s Law: 成功的复杂系统源于简单的可行系统。切勿试图从头构建复杂的完美系统，应逐步迭代。
   - KISS: 保持简单。任何增加的复杂性都是潜在的开销和错误源。
   - Zawinski’s Law: 程序会不断膨胀直到包含邮件功能。若缺乏清晰导向，软件终将因功能蔓延而臃肿。
   - Sturgeon’s Law: 90% 的东西都是垃圾。接受大部分代码或组件可能存在瑕疵的现实。
   - Postel’s Law: 严于律己，宽以待人。发送数据应保守，接收数据应开放，以增强系统鲁棒性。
   - Knuth’s Optimization Principle: 过早优化是万恶之源。在遇到性能瓶颈前，应优先保证代码可运行，而非过度优化。

2. 架构与组织结构
   - Conway’s Law: 系统架构必然反映组织的沟通结构。改变代码前需先调整组织架构（反向康威操作）。
   - Hyrum’s Law: 用户会依赖 API 的所有可观察行为，即使是意外行为。这使得成熟的系统维护兼容性极其昂贵。
   - CAP Theorem: 分布式系统无法同时满足一致性、可用性和分区容错性。必须在网络分区发生时做出明确取舍。
   - Amdahl’s Law: 并行加速效果受限于非并行的串行部分。优化瓶颈比单纯增加资源更有效。

3. 时间管理与估算
   - Hofstadter’s Law: 任务耗时总是比预期的长，即使已考虑了这条定律。未知问题总会导致工期延误。
   - Parkinson’s Law: 工作会自动膨胀以占满所有可用时间。设定明确的截止日期能有效提升效率，但需防止过度压缩。
   - Brooks’s Law: 给延期的项目增加人力只会让它更晚。新人培训的沟通成本会抵消带来的产出。
   - Murphy’s Law: 凡是可能出错的事就一定会出错。需编写防御性代码，并预设监控与回滚机制。
   - Cunningham’s Law: 在网上获得正确答案的最快方法是发布一个错误答案。利用社区纠错能力解决问题。

4. 团队动态与指标
   - Ringelmann Effect: 团队规模扩大，个人产出会下降。小团队沟通成本更低，效率更高。
   - Price’s Law: 一半的工作由总人数的平方根完成。少数核心人员承担了主要产出，需重视其留存。
   - Dunning-Kruger Effect: 能力不足者往往过度自信。新手常给出盲目乐观的估算，而专家更谨慎。
   - Goodhart’s Law: 当某项指标成为目标，它就不再是好指标。团队会为了数字好看而牺牲实际价值（如为了代码行数而复制粘贴）。
   - Gilb’s Law: 任何需要量化的事物都应以某种方式衡量。尽管有被操纵风险，但度量比不度量更有利于改进。
