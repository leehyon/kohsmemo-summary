# Building Pi With Pi
- URL: https://lucumr.pocoo.org/2026/5/24/pi-oss/
- Added: 2026-11-23 02:01:36

## TL;DR
文章反思用 Pi 开发 Pi 时，LLM 生成的低质 issue 与过度局部防御的代码会放大维护负担；应只提交亲历事实，优先消灭坏状态，并用 Agent 并行复现而非替代人类协作与上游修复。

## Summary
文章反思用 Pi 构建 Pi 的开源维护体验：Agent 改变了 issue 的角色，也放大了低质投稿与代码复杂度。作者认为根因不是 GitHub，而是人们把未经核实的 LLM 输出直接丢进协作流程；开源应回到人类协作、全局不变量与上游修复。

**底层逻辑**
- Issue 既供人读，也作为 Pi 的提示输入；错误诊断会被模型当作证据，引发连锁误判。
- LLM 倾向局部防御：为坏状态加宽容读取、回退、迁移，而非让坏状态不可能发生。
- 量增不等于维护能力增；AI 放大代码、issue 与项目数量，未增加用户和 reviewer。

**逻辑脉络**
- 先讲 slop issue：非本人语言、自信但错误的根因、复现与方案，比无诊断更糟。
- 再讲 slop 代码：缺少全局不变量，局部补丁堆积复杂度。
- 用 90 天数据说明量：3145 个外部 issue/PR，2504 个自动关闭，26% 的 issue 最终相关修复，714 个 PR 仅 60 个合并。
- 介绍 /is、prompt-url-widget、/wr 的谨慎并行工作流。
- 最后升华：开源价值在社区与共享基础，需 upstream 修复而非孤立绕过。

**Takeaways**
- 提交 issue 只写亲历事实：命令、预期、实际、日志；不要塞入 LLM 猜测。
- 修复优先消灭坏状态，而非兼容坏状态，尤其持久化 session log。
- 用 Agent 并行复现和审阅，但保留人工判断与顺序收尾。
- 维护者应把讨论拉回全局不变量和上游正确行为。
- AI 时代的开源更需要协作，而非更多隔离的机器产出。
