# The AI coding trap
- URL: https://chrisloy.dev/post/2025/09/28/the-ai-coding-trap
- Added: 2026-11-13 02:27:11

## TL;DR
AI 只加速写代码，不加速思考；把 LLM 当极快的初级工程师，用规格、文档、模块化与 TDD 等实践做它的 tech lead，才能避开 vibe coding 的复杂度之墙。

## Summary
文章认为 AI 编程工具只加速了软件开发中最不重要的一环——敲代码，真正的难点在于理解问题、界定需求与集成验证；若放任 AI 先行产出代码，人类将把大量时间花在事后理解与修补上，这就是「AI 编程陷阱」。

**逻辑脉络**
- 开发本质是问题求解，写代码只是填字；真正的认知工作发生在编码前后。
- LLM 无法一次容纳应用全貌，仍需人工评审、测试与集成，而代码若未经人类思考，这部分成本更高。
- 这解释了营销口径的「10 倍写码」与实测约 10% 的交付提效之间的落差。
- 类比「技术主管困境」：公平分派会受最慢者拖累，而包办难题短期最快，却造成知识孤岛、单点故障、倦怠与团队崩溃。
- 当代 agent 相当于「极快的初级工程师」，速度快但不会真正学习；vibe coding 与包办难题结局相同，只在简单项目成立。
- 解法是第三条路：把 LLM 纳入流程，用规范与最佳实践把速度转化为可持续交付。

**底层逻辑**
- 第一性原理：交付可用软件 ≠ 写代码，认知、验证与集成才是瓶颈。
- 工程师能力可拆为质量与速度两轴，人类与 LLM 都在两轴上提升，但 LLM 只靠上下文工程与更强的基座模型进步。
- 因此工程师应扮演 AI 的 tech lead：给结构、标准与流程，而非自己动手。

**Takeaways**
- 别用「写码速度」衡量收益，要看交付可用软件的速度。
- 把 AI 引入全生命周期：规格、文档、模块化设计、TDD、编码规范、监控。
- 用上下文工程与模块化架构控制 scope，降低事后理解成本。
- vibe coding 只适合一次性原型，复杂系统必然撞上复杂度之墙。
- 目标是 Learn. Deliver. Have fun.：让速度建立在可维护与可学习之上。
