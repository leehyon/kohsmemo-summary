# How I use LLMs as a staff engineer in 2026
- URL: https://www.seangoedecke.com/how-i-use-llms-in-2026/
- Added: 2026-06-03 05:55:34
- Tags: #llm #guide

## TL;DR
2026 年员工工程师使用 LLM 方式巨变：agent 更可靠，用于生成 PR、调查 bug 和测试，但仍需人工审查。核心是转移工作但不过度，平衡关键。

## Summary
- 核心主题：员工工程师在 2026 年使用 LLM 的方式相比 2025 年发生重大变化，主要因为 agent 能力显著提升，工作从“偶尔辅助”转向“频繁轻监督”。

- 2025 年主要用途：
  - 智能自动补全（Copilot）
  - 不熟悉领域的短期战术修改（需专家评审）
  - 一次性研究代码
  - 通过提问学习新主题
  - 最后的 bug 修复手段
  - 长篇英文通信的校对
  - 明确不用于：熟悉区域的整 PR、技术文档写作、大型代码库研究。

- 2026 年核心变化：
  - agent 变得可靠：常用 Copilot CLI 或 GitHub Copilot 应用来生成整个 PR，仅需一次编辑审查。频繁拒绝（5-6 次或更多）后才接受一个 agent 输出，但仍节省时间。
  - bug 调查：几乎所有 bug 都交给 agent，能自主诊断 80% 问题。复杂 bug 仍需人类提供额外上下文、构建心智模型、缩小搜索范围，最终由 agent 发现。
  - 写作：自己写 PR 描述、Slack 消息、ADR 等，避免过度沟通。仅当变更极简单时才保留 agent 生成的一行描述。博客仍手写，但跑 LLM 获得反馈（需忽略淡化论点的倾向）。
  - 测试与设置：将测试（curl 脚本、单元/集成测试）和本地环境设置（如 nvm 问题）交给 agent，视为低成本操作。UI 测试仍不信任 agent。
  - 代码库研究：agent 现在足够可靠，几乎总能给出正确答案。

- 不使用的场景：
  - 任何需要表达核心思想的公开沟通（除极简 PR 描述外）
  - 未经仔细审查的代码
  - UI 测试

- 核心平衡：当前核心技能是尽可能多地将工作转移给 AI agent，但不过度。许多人未充分利用 agent（不让它调查 bug、测试），也有人过度使用（让它写沟通内容、做需人工审查的大改动）。找到平衡点依然关键。
