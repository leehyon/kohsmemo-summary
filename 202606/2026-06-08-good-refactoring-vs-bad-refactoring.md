# Good Refactoring vs Bad Refactoring
- URL: https://www.builder.io/blog/good-vs-bad-refactoring
- Added: 2026-06-08 02:57:59
- Tags: #engineering #design

## TL;DR
好重构需增量进行、匹配现有风格、避免过度抽象；坏重构包括引入不一致、不理解代码、过度合并等。应保持代码可理解、可维护，提前测试并相互监督。

## Summary
- 核心主题：区分好重构与坏重构，重点在于保持代码可理解、可维护、性能稳定，避免引入不必要的复杂性与不一致。

- 六种常见坏重构类型：
   1. 大幅改变编码风格：引入新库（如 Ramda）或完全不同的范式，导致团队难以维护。好重构应沿用现有风格，仅做适度简化（如用 filter 和 map 替代手动循环）。
   2. 不必要的抽象：过度封装类与方法，增加冗余层。好重构应拆解为简单独立函数，不牺牲可读性。
   3. 引入不一致性：在统一使用 React Query 的项目中，突然用 Redux Toolkit 处理单个组件。好重构应保持与现有模式一致，复用已有方案。
   4. 不理解代码就重构：盲目删除看似冗余的缓存逻辑，导致性能下降。好重构需先理解业务意图，再优化实现（如引入带过期时间的缓存管理器）。
   5. 忽略业务上下文：为 SEO 依赖型电商网站构建客户端渲染 SPA，导致性能与索引问题。好重构应选用服务端渲染框架（如 Next.js）以匹配业务需求。
   6. 过度合并代码：统一设置所有函数的超时与内存，丢失灵活性。好重构应提供默认值的同时允许各函数覆盖参数。

- 正确重构原则：增量进行小改动，而非重写；深入理解代码后再抽象；匹配现有风格；避免过度抽象；新库或范式需团队认可；提前编写测试；同事间相互监督。

- 辅助工具：Lint 工具（Prettier、ESLint）保持风格一致；代码审查确保质量；测试框架（Vitest、React Testing Library）验证功能；AI 工具（Visual Copilot）辅助保持编码风格一致。
