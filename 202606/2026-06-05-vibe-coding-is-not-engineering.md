# Vibe Coding Is Not Engineering
- URL: https://phroneses.com/articles/build/notes/vibe-coding-is-not-engineering.html
- Added: 2026-06-05 08:28:32
- Tags: #agent #engineering

## TL;DR
vibe coding 生成可运行代码但忽略工程决策，如不变量、身份唯一性等。关键矛盾：LLM 无法替代代码生成前的系统建模与风险识别。结论：vibe coding 只适合 demo，生产必须依赖工程。

## Summary
- 核心主题 : vibe coding 产生的是代码，而工程产生的是系统。工程的关键在于代码生成之前所做的决策，这些决策决定了系统在长期生产中的安全性、一致性与可维护性。LLM 无法自动完成这些决策。

- 关键矛盾 : LLM 能快速生成可运行的代码，但无法识别并解决那些让软件安全的“工程问题”类别（如不变量、约束、失效模式、身份唯一性等）。生成的代码在演示中可行，却因缺乏系统上下文和业务需求，在生产中长期运行会失败。

- 逻辑脉络 :
  - 1. 定义差距 : vibe coding 由非软件工程师通过提示自动生成代码；而工程在代码生成前已完成问题界定、需求工程、系统建模、架构设计、非功能定义、风险识别等工作。
  - 2. 具体缺失领域（表格对比）: 不变量、身份与唯一性、约束、失效模式、耦合与顺序、状态与转换、接口与契约、边界、错误处理——工程师决定这些，LLM 生成的是忽略这些的代码。
  - 3. 后果 : 缺失工程决策导致特性碰撞、状态不可预测、部署脆弱、错误信息失去意义、简单功能难添加，系统信心崩塌。
  - 4. 演示示例 : 简单提示“添加用户账户和登录”，LLM 生成了 Flask + SQLite 示例，但未问及邮箱唯一性、账户验证、密码重置、角色、安全模型等。若邮箱不唯一，会导致登录身份混淆、密码重置影响所有同名用户、账户删除连带多个账号——生产不可容忍。
  - 5. 误解根源 : 人们误以为 LLM 像工程师一样智能，能自动捕获遗漏需求。实际 LLM 不推理系统、不构建领域模型、不追踪变更后果、不保证不变量。
  - 6. 正确做法 : 在生成代码前，必须自行决定：什么必须始终为真（不变量）、什么使实体相同（身份规则）、系统绝不允许什么（约束）、出错时如何表现（失效模式）。LLM 无法替代这些工程决策。
  - 7. 结论 : vibe coding 得到可丢弃的 demo；将它推向生产，必须依靠工程。
