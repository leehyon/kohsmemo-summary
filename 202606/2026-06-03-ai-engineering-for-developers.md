## TL;DR
AI 工程将预训练模型集成到产品，技术栈分三层。适应 LLM 按成本排序：提示工程、RAG、微调。模型选择需多模型路由。规划设检查点，注意非确定性、成本与维护。评估用程序化指标和 LLM 评判。

## Summary
AI 工程的核心是将预训练的基础模型集成到产品系统中的工程实践，区别于 ML 工程（训练模型）和全栈工程（传统后端）。

- 技术栈分为三层：应用层（提示、RAG、代理、业务逻辑）、模型开发层（微调、蒸馏，大多数团队可选）、基础设施层（GPU、推理服务器、向量数据库）。
- 适应 LLM 的三种方法按成本排序：先提示工程（修改输入）、再 RAG（运行时检索上下文）、最后微调（修改权重）。不要跳过步骤。
- 模型选择需考虑任务适配、成本、延迟、上下文窗口、结构化输出支持及部署位置。通常应使用多模型路由：SLM 处理简单任务，中端模型处理多数任务，前沿模型处理困难任务。
- 规划 AI 应用需要设置质量检查点：用例评估（是否容忍概率输出）、期望设定（开发时间约为常规功能 2 倍）、里程碑（先“勉强可用”，再评估流水线，最后生产加固）、持续维护预算（模型漂移、提示退化）。
- 开发部署维护的挑战：提示非确定性（无法单元测试）、推理慢且昂贵（需缓存、批处理、路由）、模型版本更新可能改变输出、令牌化变化、幻觉演变、安全对抗（提示注入）。
- 基础模型关键概念：训练数据决定语言覆盖与领域能力；架构为 decoder-only transformer；模型大小重要性下降，推理模型引入“测试时计算”维度；SLM 适合路由与轻量任务；多模态输入现为默认能力；结构化输出应使用 API 原生 JSON 模式；模型本质是概率分布，需为输出变化构建系统（日志、种子、评估）。
- 提示工程：编程式调用（原始 API 或 LangChain 等框架）；使用模板分离指令与用户输入，防范注入；区分系统提示（稳定指令）与用户提示（动态输入）；上下文长度大但需注意“中间丢失”现象；最佳实践包括清晰指令、充分上下文、任务分解、请求推理、迭代版本；将提示作为代码管理（git 版本 + CI 评估）；防御提示注入没有纯提示方案，需架构隔离。
- 评估是 AI 工程核心：可用程序化指标（功能正确性、相似度）、LLM 作为评判（用于主观标准，注意模型偏好偏见）、比较评估（配对排序优于打分）。评估标准优先级：领域能力 > 生成质量 > 指令遵循 > 成本与延迟。搭建最小可行评估流水线：代表性数据集 + 评分函数 + CI 集成。人力评估（样本抽查）、A/B 测试、红队应为持续流程。
