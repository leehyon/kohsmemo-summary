# Everything I know about good API design

## TL;DR
本文系统性地总结了 API 设计的关键原则：以不破坏用户空间为核心，平衡熟悉度与灵活性；强调产品价值的重要性，并提供实用建议如幂等性、速率限制、游标分页等。

## Summary
本文作者分享了关于良好 API 设计的原则，核心在于在熟悉度与灵活性之间取得平衡，并强调不破坏用户空间是首要职责。

**逻辑脉络**
- 好的 API 是无聊的，用户应能直觉使用，无需费力理解。
- API 难以更改，因此设计需谨慎；打破兼容性会伤害用户并导致迁移成本。
- 版本控制是必要之恶，但应作为最后手段，因为它增加维护复杂性和用户困惑。
- 产品质量比 API 优雅更重要：用户因产品价值而来，而非 API 设计；但糟糕的产品设计会导致 API 同样糟糕。
- 认证应支持长期 API 密钥，降低非工程师用户的门槛。
- 幂等性键确保重试安全，尤其对写操作；删除操作通常天然幂等。
- 速率限制和熔断机制是必需的，因为 API 可被代码高速调用。
- 分页应使用游标分页以应对大数据集；可选字段降低开销，但 GraphQL 并非总是最佳选择。
- 内部 API 与公共 API 不同，因用户群体专业且可强制升级。

**Takeaways**
- 首要原则：永远不要破坏用户空间；任何非向后兼容的变更都应通过版本控制谨慎进行。
- 产品价值优先于 API 质量：只要产品有吸引力，即使 API 糟糕也会有用户；但糟糕的产品设计会拖累 API。
- 为高风险的写操作实现幂等性，使用幂等性键；速率限制和熔断机制防止滥用。
- 使用游标分页处理大规模数据集；将昂贵字段设为可选，但避免过度设计如 GraphQL。
- 支持长期 API 密钥简化认证；内部 API 可更灵活，但需同样注重稳定。
