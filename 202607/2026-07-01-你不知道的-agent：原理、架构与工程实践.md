# 你不知道的 Agent：原理、架构与工程实践

## TL;DR
本文系统梳理 Agent 工程实践，强调 Harness、上下文工程、工具设计等因素比模型本身更关键，并提供 OpenClaw 落地案例和反模式总结。

## Summary
文章系统梳理了 Agent 架构的核心工程要素，涵盖控制流、上下文、工具、记忆、多 Agent 组织、评测与安全等，指出更昂贵的模型未必带来同比例提升，而 Harness（测试与约束基础设施）和工具定义的清晰度对系统成功率影响更大。

**逻辑脉络**
- 从 Agent Loop 的感知 - 决策 - 行动 - 反馈循环切入，对比 Workflow 与 Agent 的区别，介绍五种控制模式及选型原则。
- 强调 Harness 比模型更关键：验收基线、执行边界、反馈信号、回退手段是系统收敛的基础，引用 OpenAI Codex 案例。
- 上下文工程旨在防止 Context Rot，通过分层管理和压缩策略维持信号密度。
- 工具设计遵循 ACI 原则：面向 Agent 目标，定义中给出示例、边界和错误修正建议。
- 记忆系统分为四类，通过 MEMORY.md、Skills 按需加载和可回退整合实现跨会话一致性。
- 长任务通过 Initializer + Coding Agent 模式、状态外化到文件系统来跨 session 续跑。
- 多 Agent 组织需先有任务图和隔离边界，子 Agent 只回传摘要。
- 评测需区分 Pass@k 和 Pass^k，先修评测环境再改 Agent。
- 可观测性：Trace 记录完整交互，事件流做底座，人工标注与 LLM 自动评估结合。

**Takeaways**
- Agent 核心循环稳定，新能力通过工具扩展、提示结构调整、状态外化实现。
- Harness（测试验证基础设施）往往比模型能力更决定系统能否收敛。
- 上下文工程重点是防 Context Rot：分层管理、压缩策略、Skills 按需加载。
- 工具设计面向 Agent 目标（ACI），调试时优先检查工具描述而非模型能力。
- 先搭建评测环境并验证其可靠性，再基于结果调整 Agent，避免环境噪声误导。
